# FUTBA

Стартовый каркас магазина футболок: Angular 21, Rust (Axum), PostgreSQL 17,
Redis 7, Prometheus и Grafana. Каждый сервис запускается в отдельном контейнере.

## Запуск

Нужен Docker с Compose v2.

Docker-сборка использует кеш BuildKit: Cargo сохраняет скачанные зависимости и
скомпилированные библиотеки между сборками, npm — скачанные пакеты. Слой `npm ci`
переиспользуется, пока не изменились `package.json` или `package-lock.json`.
Rust-кеш сборки разделён по архитектуре и версии компилятора; исполняемый файл
копируется из кеша в образ отдельно. Первая сборка после этого изменения ещё
будет полной — ускорение появится при последующих обновлениях на том же сервере.
Кеш локален для Docker builder; очистка build-кеша потребует прогрева заново.

Обновление уже запущенного проекта (существующий `.env` сохраняется):

```sh
git pull --ff-only origin main
docker compose up -d --build
```

```sh
cp .env.example .env
# Задайте ADMIN_PASSWORD в .env перед первым запуском
docker compose up --build -d
```

- Магазин: http://localhost:4200
- API: http://localhost:8080/api/products
- Проверки: `/health` (процесс), `/ready` (PostgreSQL)
- Метрики API: http://localhost:8080/metrics
- Prometheus: только внутри Docker, `http://prometheus:9090` (источник Grafana).
- Grafana: http://localhost:3000 — пользователь `admin`, пароль из `.env`.

Grafana также доступна из интернета по `http://<IP-сервера>:3000`.
Порт TCP 3000 должен быть разрешён в сетевом экране провайдера VPS.
Вход: `admin`, пароль — `GRAFANA_ADMIN_PASSWORD` из серверного `.env`,
заданный при первом запуске Grafana. Авторизация обязательна, регистрация отключена.
До настройки HTTPS соединение использует незашифрованный HTTP.
Чтобы применить изменение публикации порта без пересборки приложения:

```bash
git pull --ff-only origin main
docker compose up -d --no-deps grafana
```

В Grafana автоматически создаются источник Prometheus и дашборды здоровья API, PostgreSQL и бизнеса.
Счётчик `http_requests_total` содержит метки route и status.
Миграции выполняются при старте backend и добавляют демонстрационные товары.
Цены хранятся целым числом в копейках. Публичный каталог (включая категории и архив), страницы товаров и витрина
кешируются в Redis. Ключи `catalog:v1:<версия>:<ресурс>` живут до часа.
Создание, редактирование, удаление товара и сохранение настроек витрины повышают
общую версию в той же транзакции PostgreSQL. Следующий запрос использует новую
версию; старые ключи удаляются по TTL или LRU. Это работает и при сбое Redis во
время изменения товара: устаревшие ключи не станут актуальными после восстановления.
Каждый запрос проверяет версию одним коротким SQL-запросом, содержимое берёт из кеша.
Чтение и запись Redis ограничены 150 мс каждое; при ошибке API читает PostgreSQL.
Ошибки/404 и JSON больше 2 МБ не кешируются. Лимит Redis — 128 МБ, `allkeys-lru`.
Сессии, чаты, заявки и административные ответы не кешируются; фотографии уже
имеют долгосрочный HTTP-кеш браузера. Попадания/промахи/ошибки видны в Grafana.

## Разработка

```sh
# Инфраструктура
docker compose up -d postgres redis prometheus grafana
# Backend (Rust 1.91+), из backend/
DATABASE_URL=postgres://user:password@localhost:5432/tee_trade REDIS_URL=redis://localhost:6379 RUST_LOG=info cargo run
# Frontend (Node.js 22.12+), из front/
npm ci
npm start
```

PostgreSQL и Redis по умолчанию доступны только в сети Compose. Для локального
backend добавьте проброс `127.0.0.1:5432:5432` и `127.0.0.1:6379:6379` в локальный
`compose.override.yaml` (он не должен содержать секретов). Подставьте параметры из `.env`.
Фронтенд перенаправляет `/api` на localhost:8080 через dev proxy.

```sh
# Проверки
cd backend
cargo fmt --check
cargo check --locked
# Из front/
npm run build
# Из корня
docker compose config -q
docker compose logs -f
docker compose down
```

Данные PostgreSQL, Prometheus и Grafana сохраняются в именованных томах.
`docker compose down -v` удаляет эти данные.
`.env` не коммитится. Пароли из примера предназначены для локального запуска.
Это стартовый каталог; корзина, заказы, платежи и авторизация пока не реализованы.

## Страницы и каталог

- `/` — главная с разделами и подборкой товаров.
- `/catalog` — весь каталог; `/catalog/sneakers`, `/catalog/t-shirts`,
  `/catalog/accessories`, `/catalog/headwear` — отдельные категории.
- `/product/:id` — описание, характеристики и галерея товара.
- `/about` — о проекте.

Общее меню доступно на каждой странице. В каталоге можно сортировать по цене
и году выпуска. Карточка показывает одно основное изображение; на странице
товара доступны все загруженные изображения.

API: `GET /api/products?category=sneakers`, `GET /api/products/:id`.
Неизвестная категория возвращает 400, отсутствующий товар — 404.
Миграция `0002_catalog.sql` добавляет характеристики, категории и JSONB-галерею.
Каждое изображение имеет `url`, `alt` и `kind` (`front`, `detail`, `label`).
После миграции `0004_optional_products.sql` фотографии и подписи необязательны.
База проверяет структуру изображений и непустые ссылки. Админка проверяет наличие загруженного файла, формат и размер. Администратор
назначает роль «Ярлычок» и проверяет содержание снимка.

Сейчас каталог содержит **демонстрационные товары и SVG-иллюстрации**.
Они помечены `is_demo`; шаблон ярлычка не является фотографией реального изделия.
Демо-иллюстрации находятся в `front/public/images/`. Реальные фотографии загружаются через `/admin` и сохраняются в постоянном томе `media_data`; в базе остаются метаданные. Отдельного поля для ярлычка нет.

После обновления запустите `docker compose up --build -d` — миграция применится
автоматически к существующей базе. Старые тома удалять не нужно.

Интеграционная проверка запущенного приложения:

```sh
python3 scripts/smoke_test.py
```

Проверяются категории, поля и галереи товаров, доступность локальных изображений,
ответы 400/404 и открытие внутренних страниц напрямую через nginx.

Проверка ограничений галереи (изменения откатываются):

```sh
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1' < scripts/check_gallery.sql
```

## Администрирование

Адрес: http://localhost:4200/admin. Ссылки на админку нет в публичном меню.
В системе один администратор: логин задаётся через `ADMIN_USERNAME` (по умолчанию
`arzamas`), начальный пароль — через `ADMIN_PASSWORD` в локальном `.env`.
Пароль не записывается в исходники или миграции. При первом старте сохраняется
Argon2id-хеш в PostgreSQL. При следующих стартах существующий аккаунт сохраняется:
изменение `.env` не меняет пароль уже созданного администратора.

После входа доступны:

- добавление и редактирование товаров со всеми характеристиками;
- удаление товаров с подтверждением: товар убирается из каталога и подборок главной, опустевшие подборки отключаются; метаданные и файлы фотографий удаляются вместе с товаром, кроме используемых другими товарами;
- единое поле загрузки до 12 фотографий: drag-and-drop на десктопе, кнопка выбора нескольких фото на телефоне; повторные выборы добавляются к уже загруженным;
- независимый выбор обложки каталога и фото для карусели на главной, подписи и порядок фотографий;
- выбор и порядок товаров в верхней галерее и популярной подборке;
- заголовки, категории и текстовый блок главной, включение/выключение разделов.

Файлы JPEG, PNG и WebP до 8 МБ проверяются декодером, ориентируются по EXIF,
уменьшаются до 2400 пикселей по большей стороне и сохраняются как JPEG в томе
`media_data`. Метаданные (ID, SHA-256 и размеры) остаются в таблице `media`.
Удаление фото из формы отсоединяет его от товара; сам файл остаётся в хранилище.
Для резервной копии нужны **и PostgreSQL, и media_data**; одной копии базы недостаточно.

Сессия действует 8 часов, хранится в HttpOnly / SameSite=Strict cookie и отзывается
при выходе. Все административные операции защищены серверной проверкой сессии,
изменения — CSRF-токеном. После 15 попыток входа за 5 минут новые попытки временно
блокируются (общий лимит для единственного администратора).
Для HTTPS-развёртывания задайте `COOKIE_SECURE=true` и `APP_ORIGIN` равным точному
адресу сайта. Локально используется `http://localhost:4200`.

Редактирование товара обновляет версию кеша каталога в той же транзакции.
Главная получает содержимое через `GET /api/storefront`; настройки сохраняются
в PostgreSQL. Данные для инициализации текущей витрины переносит миграция `0003`.

Проверка админки на локальном Compose (создаёт временный товар и изображения,
проверяет изменения витрины, восстанавливает витрину и удаляет только свои фикстуры):

```sh
python3 scripts/admin_smoke_test.py
```

Тест читает локальные учётные данные из `.env` или переменных окружения и не
выводит их. Проверяет авторизацию, CSRF, загрузку файлов, пустую карточку и необязательные фотографии,
создание/редактирование товара, актуальность кеша, витрину и отзыв сессии.

Поля товара необязательны: можно сохранить пустую карточку или одну фотографию без ярлычка. Неуказанные цена и год хранятся как NULL; ограничения длины, формата, цены и загрузки файлов сохраняются.

### Аккаунты покупателей

`/account` открывает регистрацию и вход по логину и паролю. Регистрация требует логин (3–40 букв, цифр, точек, дефисов или подчёркиваний), пароль (не менее 8 символов) и его подтверждение. Логины уникальны без учёта регистра; логин администратора зарезервирован. После регистрации пользователь автоматически входит в аккаунт.

Пользователи сохраняются в `customers`; пароли хешируются Argon2, сессии хранятся в `customer_sessions` с хешем токена и сроком 7 дней. Cookie `tt_customer` — HttpOnly, SameSite=Strict; Secure включается через существующую настройку `COOKIE_SECURE`. Пользовательские сессии не дают доступа к API администратора. API: `/api/auth/register`, `/api/auth/login`, `/api/auth/session`, `/api/auth/logout`. Выход требует CSRF-токен.

Проверка: `python3 scripts/customer_smoke_test.py` создаёт временного пользователя и удаляет его после проверки.

### Чаты по товарам

У покупателя кнопка «Написать» открывает модальное окно; повторное открытие возвращает тот же диалог по товару. Список переписок для обеих ролей открывается колокольчиком в верхнем меню в правой боковой панели. Старые списки в профиле и админке убраны. Панель показывает собеседника, товар, последнее сообщение с временем справа (для прошлых дней — с датой) и непрочитанные; настройки звука находятся здесь же. Список обновляется при WebSocket-уведомлении, открытии панели и каждые 10 секунд, когда вкладка видима. Сообщения и индикатор набора передаются по WebSocket. Enter отправляет сообщение, Shift+Enter переносит строку. Текст ограничен 4000 символами, вложения не предусмотрены.

Миграция `0006_chats.sql` создаёт `chats` и `chat_messages`. История сохраняется в PostgreSQL; последние 100 сообщений загружаются при подключении, более ранние — кнопкой «Предыдущие сообщения». При обрыве связи клиент переподключается; идентификатор сообщения защищает от дублей. Удаление товара сохраняет переписку и снимок его названия/номера. Покупатель получает только собственные чаты, администратор — все; сессия проверяется при подключении, отправке, получении событий и каждые 15 секунд. WebSocket требует точного Origin из `APP_ORIGIN`.

WebSocket endpoints: `/api/auth/chats/ws?chat_id=…`, `/api/admin/chats/ws?chat_id=…`. Nginx и dev proxy настроены на Upgrade. Между соединениями одного процесса события передаются через Tokio broadcast; перед запуском нескольких реплик backend потребуется общий транспорт событий (например, Redis Pub/Sub).

Проверка: `node scripts/chat_smoke_test.mjs` (после `npm ci` в `front`). Создаёт временные товары/аккаунты, проверяет обмен по WebSocket в обе стороны, набор текста, права, восстановление и пагинацию истории, отсутствие дублей и отзыв сессии; затем удаляет свои данные.

Уведомления приходят обоим собеседникам на любой странице после входа: администратору через `/api/admin/chats/events`, покупателю через `/api/auth/chats/events` только для его переписок. Тост содержит ссылку на диалог и кнопку закрытия с областью нажатия 44×44 px. При открытой панели или модальном чате тост отображается внутри активного диалога, чтобы оставаться доступным для касаний. Звук воспроизводится общим HTML-аудиоплеером после взаимодействия с браузером, включая завершённое касание на телефоне. В меню есть кнопки «Включить звук» и «Проверить звук»; отключение звука сохраняется в браузере. До первого разрешённого браузером взаимодействия звук может быть заблокирован, тосты при этом работают. При переподключении загружаются последние пропущенные уведомления (до 100). Звуковые и визуальные уведомления предназначены для открытого сайта, не заменяют системные push-уведомления при закрытом браузере.

Проверка уведомлений и изоляции переписок: `node scripts/chat_smoke_test.mjs` (запущенный Docker Compose). Проверка активации звука, блокировки autoplay и сохранения настройки: `node scripts/notification_sound_test.cjs` (после `npm ci` в `front`).

На мобильных устройствах чат занимает видимую область экрана, учитывает появление клавиатуры и блокирует прокрутку фоновой страницы. При задержке подключения свыше 10 секунд выполняется повторная попытка; истёкшая сессия и недоступный чат показываются отдельно.


Миграция `0007_chat_read.sql` хранит границы прочитанных сообщений отдельно для администратора и покупателя. Колокольчик показывает сумму входящих непрочитанных сообщений. Клиент подтверждает только полученные сообщения, когда открыта видимая переписка и история прокручена вниз; сервер проверяет владельца чата и CSRF, ограничивает отметку существующими сообщениями и не позволяет откатить её назад. Счётчик сохраняется после обновления страницы.

Фото для главной сохраняется флагом `carousel` в выбранном элементе `images`. API допускает не более одного такого фото. Для старых товаров без этого флага карусель использует обложку или первую фотографию; существующие фотографии ярлычков сохраняются как обычные изображения. При удалении выбранного фото в редакторе назначается оставшаяся обложка. Мобильный выбор запускает системное меню: несколько файлов можно выбрать из галереи, снимки камеры добавляются по очереди; набор пунктов зависит от браузера и ОС.

## Сетевой доступ на VPS

Grafana опубликована на TCP 3000, анонимный вход и её `/metrics` отключены.
Prometheus не публикует порты на хост; backend доступен на хосте только через
127.0.0.1:8080. Front блокирует `/metrics`; сбор метрик внутри Docker сохраняется.
Не добавляйте публичные пробросы 8080/9090 или проксирование `/metrics` в серверный nginx.
Docker обходит часть правил UFW, поэтому ограничения Compose обязательны.

После обновления проекта примените на Ubuntu (22 замените на фактический SSH-порт):

```bash
docker compose up -d --build
sudo bash scripts/setup-firewall.sh 22
```

Скрипт сохраняет существующие правила, разрешает SSH, 80, 443 и 3000, запрещает
входящие 8080/9090 и включает UFW. В firewall провайдера также разрешите SSH,
80/443/3000 и закройте 8080/9090. Не меняйте SSH-порт в команде наугад.
Проверка с другого компьютера: порт 3000 показывает вход Grafana, 8080/9090
недоступны; `/metrics` сайта возвращает 404. В Grafana дашборд продолжает получать данные.

## Заявки на товары

Авторизованный покупатель может оставить заявку на странице товара: фамилия,
имя, контакт для связи и город обязательны, отчество необязательно. На телефоне
форма открывается на весь экран и блокирует прокрутку страницы под ней.
В профиле отображаются собственные заявки, их данные и статусы.

В админке раздел «Заявки» содержит активные заявки и архив. Статусы меняются
последовательно: «Новая» → «В работе» → «Завершена». Завершение переносит заявку
в архив. Из заявки администратор открывает чат с её покупателем именно по этому
товару. Название и номер товара, данные заявки и переписка сохраняются после
удаления товара. Одновременно разрешена одна активная заявка покупателя на товар.

Новая заявка вызывает тост и звук у администратора, изменение статуса — у её
покупателя. Ссылка в тосте открывает заявку. Используется общая настройка звука
чатов; браузеру требуется первое взаимодействие для воспроизведения аудио.
События заявок передаются через WebSocket уведомлений чата, с отдельным курсором
`request_after` и повторной доставкой из базы после временного сбоя сети.
Списки чатов обновляются по событиям сообщений, создания чата и прочтения,
без периодического HTTP-опроса. После переподключения список загружается заново. При первом открытии страницы старые события
не озвучиваются. Это уведомления внутри сайта, не системные push-уведомления.

Миграция 0008 создаёт заявки и журнал событий. Доступ ограничен серверными
сессиями, изменение данных защищено CSRF; покупатель не может менять статус
или читать чужие заявки. Контактные данные не включаются в тосты.
Проверка: `node scripts/request_smoke_test.mjs` при запущенном Docker Compose.

## Дашборды мониторинга и бизнеса

В Grafana автоматически создаются три дашборда:
- **FUTBA — здоровье API**: /d/tee-trade-api — доступность, RPS,
  p50/p95/p99 до заголовков ответа, 4xx/5xx, текущие запросы, WebSocket,
  пул соединений и попадания/ошибки кеша.
- **FUTBA — здоровье PostgreSQL**: /d/tee-trade-postgres — подключения,
  лимит соединений, commit/rollback, размер базы и таблиц, блокировки,
  длительные транзакции, deadlock, буферный кеш и autovacuum.
- **FUTBA — бизнес и конверсии**: /d/tee-trade-business — регистрации,
  просмотры, посетители, заявки, текущий архив/очередь, сообщения, активные
  переписки и конверсии. Окно показателей выбирается отдельно: 24h/7d/30d/90d.
  Верхний выбор времени Grafana задаёт диапазон графиков, а не окно карточек.

PostgreSQL опрашивается postgres-exporter v0.18.1 независимо от процесса API.
Exporter использует серверные POSTGRES_USER/POSTGRES_PASSWORD, не публикует
9187 на хост. Prometheus и /metrics по-прежнему недоступны из интернета.
Не добавляйте публичный проброс 9187, 9090 или 8080. Дашборд не измеряет
свободное место диска VPS: для этого нужен отдельный мониторинг хоста.

Просмотры пишутся только при загрузке страницы товара браузером через
POST /api/auth/product-views/{id}. Просмотр администратором в UI и демотовары
исключены. Повторы одной пары посетитель+товар внутри фиксированного
30-минутного интервала считаются один раз. Для гостей используется HttpOnly
cookie tt_visitor (90 дней); в базе хранится хеш, IP и user-agent не записываются.
Авторизованный просмотр связывается с покупателем; старые анонимные просмотры
после входа не объединяются. Идентификаторы и контактные данные не попадают
в метки Prometheus. Детальные просмотры очищаются после 98 дней.

Бизнес-метрики — **gauge-снимки из PostgreSQL**, а не счётчики HTTP-запросов:
перезапуск API не обнуляет бизнес-данные. Снимки обновляются раз в минуту,
проверки PostgreSQL/Redis — каждые 15 секунд. При ошибке сбора или возрасте
снимка больше 180 секунд бизнес-панели скрывают устаревшие значения.
История просмотров начинается с миграции 0009; старые регистрации, заявки
и сообщения рассчитываются по сохранённым записям.

Конверсии:
- просмотр → заявка/сообщение: доля авторизованных пар покупатель+товар с
  просмотром в выбранном окне, после которого за 7 дней возникло нужное событие;
- первое сообщение → заявка: доля пар с первым сообщением покупателя в окне
  и последующей заявкой по тому же товару в течение 7 дней;
- регистрация → заявка: доля зарегистрировавшихся в окне покупателей,
  оставивших заявку за 7 дней после регистрации.

У новых когорт ещё не истекло 7 дней; при нулевом знаменателе отображается
«Нет данных». Это последовательность событий, а не доказанная причинность.
Сообщение не обязательно предшествует заявке: это две ветки после просмотра.

Применение на VPS (новых переменных .env не требуется):

```bash
git pull --ff-only origin main
docker compose up -d --build
docker compose restart prometheus grafana
```

Перезапуск Prometheus нужен для загрузки нового scrape job. После запуска
дайте метрикам 1–2 минуты; графикам задержек нужен трафик.

Проверки: python3 scripts/business_metrics_test.py, node scripts/analytics_smoke_test.mjs,
python3 scripts/check_dashboards.py. Последняя выполняет все запросы дашбордов
в локальном Prometheus. Генератор JSON: python3 scripts/generate_dashboards.py.

Семантика показателей: [документация PostgreSQL](https://www.postgresql.org/docs/17/monitoring-stats.html).
Конфигурация: [postgres-exporter v0.18.1](https://github.com/prometheus-community/postgres_exporter/tree/v0.18.1).

### Превью фотографий

Миграция `0010_media_previews.sql` добавляет сохраняемое JPEG-превью до 480×480
с сохранением пропорций. Новые загрузки сразу получают превью; для существующих
фото оно создаётся при экспорте или первом GET `/api/media/{id}/preview`.
После миграции 0014 оригиналы и превью сохраняются в файловом томе.
Карточки в каталоге и подборках главной используют превью. Страница товара и
карусель продолжают использовать большой вариант `/api/media/{id}` (до 2400×2400,
как и раньше). Оба варианта кешируются браузером; удаление записи media удаляет
также превью. Проверка: `python3 scripts/admin_smoke_test.py`.

### Архив и загрузка фотографий

В редакторе товара флаг «Продано» переносит товар в `/archive`: он пропадает из
обычного каталога и подборок главной. Снятие флага возвращает товар в продажу.
Архив использует ту же сетку карточек; на странице проданного товара нет кнопок
чата и заявки. API также запрещает новые заявки и открытие чата через такой товар;
существующая переписка сохраняется. Категория `hoodies` отображается как «Худи».
Обложка всегда показывается первой в галерее страницы товара.

В админке «Товары» показывает только доступные товары, «Архив» — проданные.
Оба списка загружают только превью фотографий. Кнопка «Перенести в архив»
меняет только статус через `POST /api/admin/products/{id}/archive` и обновляет
ревизию публичного кеша. В архиве у записи доступна только кнопка удаления.
Окончательное удаление товара удаляет его чаты, сообщения, заявки, события заявок
и просмотры каскадно (миграция 0013); изображения и превью удаляются, если их
не использует другой товар. Старые записи о товарах, удалённых до миграции,
не очищаются автоматически. Учётные записи покупателей сохраняются.

Файлы из множественного выбора отправляются последовательно. После 45 секунд
без HTTP-событий загрузка файла завершается ошибкой; остальные файлы продолжают
обрабатываться. Неудачные файлы можно повторить отдельной кнопкой без повторной
отправки успешных. Ограничения: 12 фотографий на товар, JPEG/PNG/WebP до 8 МБ каждая.
Проверки: `node scripts/upload_queue_test.cjs`, `python3 scripts/admin_smoke_test.py`,
`node scripts/request_smoke_test.mjs`.

### Загрузка фронтенда и Lighthouse

В админке товары, архив, активные/завершённые заявки и выбор товаров для витрины
подгружаются при прокрутке по 8 записей (до 700 px — по 4). Поиск товаров выполняется
на сервере по названию и бренду; смена поиска или раздела начинает загрузку заново.
Ошибку следующей порции можно повторить без потери уже загруженных строк.
Редактор товара и заявка из уведомления запрашиваются отдельно по ID; бренды и
названия уже выбранных для витрины товаров не требуют загрузки полного каталога.
Настроенные подборки по-прежнему ограничены 24 ID каждая и доступны для перестановки.
Проверки: `node scripts/admin_paging_test.cjs`, `python3 scripts/admin_smoke_test.py`,
`node scripts/request_smoke_test.mjs`.

Каталог и публичный архив подгружают товары при достижении конца списка:
по 8 на десктопе и по 4 при ширине до 700 px. Новые карточки добавляются снизу;
смена категории или сортировки отменяет текущий запрос и начинает список заново.
`GET /api/products/page` принимает `limit`, `offset`, `sort`, `category`, `sold`
и возвращает `items` и `total`. Сортировка выполняется в БД для всего результата,
с ID как дополнительным ключом порядка. Страницы кешируются с общей ревизией
каталога. Старый `/api/products` сохранён для совместимости.
Проверки: `node scripts/catalog_paging_test.cjs`, `python3 scripts/admin_smoke_test.py`.

В редакторе товара бренд выбирается через контрол с текстовым поиском или вводится
новый. Варианты берутся из существующих товаров, включая архив; новое название
становится общим вариантом после сохранения товара. Поле остаётся необязательным.
В каталоге свёрнутый по умолчанию фильтр «Бренды» позволяет выбрать несколько
тегов (логика ИЛИ). API страницы принимает `brands` как JSON-массив строк и
возвращает доступные `brands` по всей текущей категории и статусу, независимо
от страницы и выбора внутри самого фильтра брендов. Пустые названия исключаются,
сравнение не зависит от регистра. Выбор брендов сбрасывает пейджинг, смена категории
сбрасывает выбранные бренды. Ключ Redis включает нормализованный набор брендов.

Карусель и главное фото на странице товара сначала показывают превью 480 px.
Большой снимок загружается после превью и заменяет его только после декодирования;
переключение фотографии отменяет устаревшую загрузку. Миниатюры страницы товара
используют только превью. Карусель заранее загружает превью следующего слайда.
Размер кадра фиксируется адаптивно, чтобы загрузка фото не сдвигала страницу.

Nginx сжимает текстовые ответы gzip и кеширует файлы JS/CSS с хешем имени на год,
а index.html требует перепроверки. Интерфейс чатов загружается отложенно.

Мобильный Lighthouse 12.8.2, локальная production-сборка, 04.11.2026:

### Переход фотографий из PostgreSQL в файлы (VPS)

Миграция `0014_media_files.sql` сохраняет существующие `content`/`preview` и добавляет
контрольные суммы и размеры. Новые загрузки **сразу файловые**: backend записывает
оба файла через временные имена, fsync и атомарное переименование, затем фиксирует
метаданные. Ответ об успешной загрузке приходит после этого. Обработка EXIF,
качество JPEG, размеры, обложка, фото карусели и текущие URL не меняются.

Файлы: `/data/media/{id}.jpg` и `/data/media/{id}.preview.jpg` в named volume
`media_data`. Backend работает от UID 10001, Nginx получает том только для чтения.
Одноразовый `media-init` задаёт права каталога. Nginx отдаёт существующие файлы
напрямую, с `sendfile`, MIME image/jpeg, immutable-кешем и поддержкой Range.
Если старый файл ещё не выгружен, запрос передаётся backend: он экспортирует запись
из базы под блокировкой строки. Ссылки `/api/media/{id}` и `/api/media/{id}/preview`
сохраняются, изменения `products.images` не нужны. Удаление метаданных ставит
устойчивое задание удаления файлов в той же транзакции. Обычно файлы удаляются
сразу после удаления товара; при ошибке задание повторяется каждые 30 секунд.
Общие фотографии остаются, пока есть ссылающийся на них товар.

Первое обновление на VPS после получения этого коммита:

```bash
cd ~/tee-trade
git pull --ff-only origin main
./scripts/deploy-media.sh
```

Скрипт сначала собирает образы без остановки сайта, затем останавливает backend/front
на время резервного копирования и переноса (в это время сайт временно недоступен).
В `backups/media-ДАТА-ВРЕМЯ/` сохраняются `before.dump`, `after.dump`, `media.tar.gz`
и контрольные суммы. Экспорт проходит по одной записи, проверяет оба файла по
SHA-256 и наличие записей media для ссылок товаров. Повторный запуск допустим.
При ошибке скрипт останавливается, не очищает старые байты и сообщает путь копии.
Нужно достаточно свободного места под выгрузку и резервные копии. Скопируйте
резервную копию также за пределы VPS.

После проверки сайта, загрузки новых фото и наличия резервной копии можно освободить
место, занятое старыми байтами внутри БД:

```bash
docker compose exec -T backend tee-trade-api media-prune-db
docker compose exec -T backend tee-trade-api media-verify
docker compose exec -T postgres sh -c 'vacuumdb -U "$POSTGRES_USER" -d "$POSTGRES_DB" --analyze --table=media'
```

Очистка проверяет контрольные суммы перед обнулением **каждой** записи; при ошибке
останавливается, ранее успешно обработанные записи уже могут быть очищены.
Продолжить можно повторным запуском после восстановления файлов. Обычный VACUUM
делает место повторно используемым PostgreSQL, но не гарантирует уменьшение файла
базы на диске. `VACUUM FULL` здесь намеренно не запускается.

Команды `media-export`, `media-verify`, `media-prune-db` также принимают необязательный
ID изображения вторым аргументом для адресной проверки. `media-export` не очищает
байты в БД; пока они сохранены, повторный экспорт восстанавливает повреждённые файлы.
После очистки восстановление оригиналов возможно из резервной копии файлов.
Не удаляйте volume (`docker compose down -v`). Для отката/восстановления нужна
согласованная пара дампа и файлов с сохранением прав; один `git reset` не возвращает
новые файловые загрузки в старую схему хранения.

Проверки: `python3 scripts/media_storage_test.py`, `python3 scripts/admin_smoke_test.py`,
`node scripts/request_smoke_test.mjs`. Тест миграции проверяет старую запись без
превью, повторный экспорт, отказ очистки при повреждении файла, восстановление,
очистку байтов, неизменность ссылок, прямую выдачу Nginx и удаление обоих файлов.
