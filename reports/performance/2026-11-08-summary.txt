FUTBA: производительность, надёжность и локальная проверка безопасности
Дата: 8 ноября 2026. VPS не изменялся. Изменения не запушены.

Что изменено
1. Nginx переиспользует HTTP-соединения к API. Connection: upgrade передаётся
   только для WebSocket. Добавлены DNS-переопределение backend в Docker и
   keepalive upstream. Это устранило воспроизводимые 502 при интенсивной нагрузке:
   connect() failed (99: Address not available), исчерпание исходящих портов.
2. Redis ConnectionManager разделяется между запросами и мониторингом; сам
   восстанавливает соединение. Сохранены TTL, проверка ревизии, инвалидация,
   обход Redis при ошибке и существующие метрики.
3. Главная получает четыре новинки сразу в /api/storefront. Полный каталог
   больше не скачивается и не сортируется в браузере ради четырёх товаров.
   Версия ключа витрины обновлена, чтобы старый JSON не использовался новой схемой.
4. Страницы вынесены из монолитного pages.ts. Основные публичные страницы
   загружаются сразу: эксперимент с lazy loading ухудшил LCP, поэтому отменён.
   Админка, аккаунт и вспомогательные страницы остаются отложенными.
   OnPush применён к карточкам, карусели и индикатору догрузки.
5. Зарезервировано место до появления контента: устранён скачок футера.
   В каталоге исправлена последовательность заголовков, оформление не изменено.
6. Миграция 0019 добавляет индексы по нормализованным массивам брендов/размеров,
   категории/архивности/цене, спискам заявок, активности чатов и непрочитанным.
   Прежние значения и связи не меняются. Проверенный EXPLAIN использует оба GIN
   индекса, запрос с комбинированным фильтром на 1000 тестовых товарах ~0.3 мс.
7. Обработка фото ограничена одной тяжёлой задачей одновременно; вычисления
   Argon2 — двумя. При перегрузке возвращается 429 с сообщением повторить запрос.
   Разрешения удерживаются и внутри blocking-задач, включая отмену HTTP-запроса.
   Это ограничивает расход CPU/памяти. Пул PostgreSQL: 10 соединений, ожидание 3 с.
8. Добавлены X-Frame-Options, nosniff, Referrer-Policy и ограниченная CSP
   (frame-ancestors/base-uri/object-src), в том числе на статических ответах.
   Политика не ограничивает script-src: это не полноценная защита от XSS.

Нагрузка
A. До: существующий локальный каталог (2 товара), тёплый кэш, JSON API,
   клиенты без пауз, четыре ступени по 10 с (10/50/100/200).
   10 клиентов: ~2344 req/s, p95 9.9 мс.
   С 50 клиентов: массовые 502 из-за отсутствия upstream keepalive.
   На 200: 11537 ответов 502 из 11540; это не полезная пропускная способность.
B. После: тот же сценарий, 200 клиентов: ~12267 req/s, p95 26.3 мс,
   123133 успешных ответов из 123133 за 10 секунд.
   Короткий тест на мощном локальном окружении; не capacity/SLA для VPS.
C. 1000 временных товаров + реальные 2. Только backend ограничен одним CPU;
   остальные контейнеры и генератор работают на мощном Mac/Docker.
   200 клиентов, пауза 1 с между запросами, 15 с: 3000/3000 ответов 200,
   ~197 req/s, p95 27.4 мс, p99 37.6 мс.
   Данные синтетические; фотографии в этом сценарии не скачивались.
D. 200 открытых WebSocket уведомлений одной тестовой учётной записи:
   все открыты через 20 с, ошибок 0, p95 handshake ~39 мс.
   Это проверка соединений, не 200 уникальных покупателей и не массовая переписка.
E. Redis выключен и включён локально. Ответ совпал с ответом из кеша,
   fallback ~157 мс; автоматическое восстановление кеша ~4.7 с.

Оценка для VPS (1 CPU / 2 ГБ)
Разумный предварительный ориентир — порядка 100–200 одновременно активных
покупателей, преимущественно просматривающих каталог, с паузами между действиями
и прогретым кэшем. Это рабочая гипотеза с запасом, а НЕ измеренный предел VPS.
Прямо подтверждены только локальные сценарии выше.
100–200 одновременно регистрирующихся, отправляющих сообщения или грузящих
фотографии — совершенно другая нагрузка; эти числа к ней не относятся.
Пропускная способность внешнего канала и размер оригинальных фото, совместная
работа PostgreSQL/Grafana/Prometheus на одном CPU, swap и сложные холодные фильтры
остаются ограничителями. Нужны VPS-замеры p95, ошибок, CPU/RAM и диска при реальном
профиле посетителей. Увеличивать max_connections на основании этих тестов нельзя.

Мини-пентест: объём и результат
Локально проверены неавторизованное чтение/изменение закрытых данных, разделение
покупателя и администратора, доступ к чужим чатам/заявкам (IDOR), CSRF/Origin,
WebSocket Origin и отзыв сессии, SQL-инъекционные строки в фильтрах/сортировке,
границы пагинации/полей, блокировка публичного /metrics, недоступные media,
SVG/неизображения при загрузке, заголовки безопасности.
В проверенных сценариях обход авторизации/SQL-инъекция не воспроизведены.
Это ограниченная проверка, не заявление об отсутствии всех уязвимостей.

Сканирование зависимостей:
- npm audit --omit=dev: 0.
- Полное npm audit: 16 moderate-зависимостей сборки, два исходных advisory
  glob/minimatch. Предлагаемый npm fix требует major-обновления Angular CLI.
  Не применялся вслепую из-за риска регрессий. Эти инструменты не входят в
  Nginx runtime. Отдельно обновить build-toolchain и прогнать CI.
  https://github.com/advisories/GHSA-3g3m-2fjr-6pw4
  https://github.com/advisories/GHSA-g3hv-75wg-m249
- OSV querybatch по 267 пакетам Cargo.lock: rsa 0.9.10, RUSTSEC-2023-0071.
  cargo tree -i rsa не показывает активных зависимостей, в том числе для
  Linux ARM64; приложение использует PostgreSQL, RSA находится в lock-файле
  optional SQLx/MySQL. Сканер lock-файла не равен доказательству эксплуатации.
  Полная проверка дерева для Linux x86_64 offline не выполнена: отсутствовал
  загруженный target-specific пакет. https://osv.dev/vulnerability/RUSTSEC-2023-0071
- Установка cargo-audit зависла на обновлении registry и была остановлена;
  вместо неё использован официальный OSV API. Это отмечено, а не выдано за
  успешно выполненный cargo-audit.

Остаточные риски / следующие шаги
- Глобальный auth throttle 100 попыток/5 минут может блокировать вход другим
  пользователям при злоупотреблении. Нужен rate limit по доверенному client IP
  на входном proxy с корректной цепочкой доверия Caddy→Nginx. Политику входа
  и доверие произвольному X-Forwarded-For в этом рефакторинге не менял.
- Устаревший GET /api/products всё ещё отдаёт весь каталог для совместимости;
  UI главной его больше не использует. Очень большой каталог требует
  прекращения использования этого endpoint внешними клиентами.
- Не добавлялся лимит числа WebSocket на аккаунт/IP; проверены 200 idle-соединений.
- Не тестировались production TLS, firewall, SSH и фактическая .env VPS.
  Для HTTPS COOKIE_SECURE должен быть true. CSP здесь ограниченная.
- Нет длительного soak-теста, проверки восстановления после убийства PostgreSQL
  или нагрузочного сценария одновременных больших загрузок и активной переписки.

Регрессия
Production-сборки Rust/Angular прошли. Пройдены: каталог/маршруты, admin CRUD,
архив и каскады, фото и очередь загрузок, размеры/бренды, 4/8 pagination и
восстановление прокрутки, навигация товара, progressive images, звук уведомлений,
регистрация/вход/CSRF, чат/typing/history/replay/read-state/ownership,
заявки/статусы/уведомления, аналитика, когортные расчёты, Redis cache recovery,
92 PromQL-выражения, разбор Redis INFO.
Исправлены устаревшие тестовые ожидания размера-строки и сохранения чатов/просмотров
после удаления товара: они противоречили уже действующей миграции 0013.
Отдельного полного ручного обхода каждого экрана на физическом телефоне не было.

Временные товары/покупатели удалены. Исходные 2 товара сохранены.
Redis перезапущен тестом, данные кэша прогреваются снова.
CPU-лимит backend восстановлен по Compose. Исходники не коммитились и не пушились.
При выкладке нужны новые backend/front и автоматическая миграция 0019; сначала
сделать дамп PostgreSQL. Не применять docker system prune -a перед сборкой.
